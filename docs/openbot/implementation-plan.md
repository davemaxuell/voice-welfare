# OpenBot implementation plan for Cheongeum

**Build the first release around a resident returning to work they already started.** Someone asks “기초연금 신청에 필요한 서류를 찾아줘”, agrees to a public lookup, and closes the app. When they return to their personal PC, “맡긴 조사 결과 읽어줘” should read the answer, identify the source and its date, and offer to open the official page. If the source omits a requirement, the resident should hear what still needs checking. This journey uses Cheongeum’s existing worker, voice interface and browser, and would benefit directly from OpenBot’s treatment of durable work and visible outcomes.

This plan targets the November 21 TypeScript service, React/Vite UI and Electron shell. The comparison uses the released OpenBot **v1.1.2** (`8826a0f`) and Cheongeum **`2bfc330`** on `feat/portal-discovery-orient`, with ongoing portal discovery, screen orientation and progress work inspected separately. The November 19 study records the earlier Python pilot. [OpenBot release](https://github.com/CopilotKit/OpenBot/releases/tag/v1.1.2) · [Earlier study](README.md) · [Cheongeum runtime](../../src/server/runtime.ts)

## Backend work for tasks that stop midway

A delegated public lookup previously timed out after 105 seconds and restarted from its original question. The worker now renews its lease during a live lookup and has a separate five-minute research budget. The next priority is the foreground review loop. A failed middle action can discard the rest of an ordered plan, and a restarted public job still lacks a record of verified steps. Before enabling another search provider such as Parallel, compare field coverage, latency and cost on the same Korean HTML/PDF fixture set. [Worker](../../src/server/workflows.ts) · [Review loop](../../src/orchestrator/review_loop.ts)

Start recording stop reasons and preserving unfinished steps alongside PRs 1 and 2. Use PR 1’s public evidence format for durable step checkpoints, and give PR 3’s inbox the resulting verified items and next decision. Recurring checks and parallel public research can then reuse the same execution and recovery rules.

## First release

PRs 1 and 2 can proceed independently. PR 3 needs PR 1’s saved-result format. Ship PR 2 as soon as its reconnect test passes. The effort ranges are planning estimates for one engineer familiar with this repo. Participant sessions and institutional setup are separate.

### PR 1 · Keep the evidence with a saved answer (2–3 engineering days)

`PublicPlanner.research` returns text and sources. `publicResult` narrows each source to `title` and `url`, and the renderer validates that same narrow shape. Passing a dated citation through the current function reproduces the loss. A person reading a result days later therefore cannot reliably distinguish the day the app checked the source from the date the agency’s information applies. [Planner](../../src/orchestrator/public_plan.ts) · [Persistence boundary](../../src/server/workflows.ts) · [Renderer contract](../../web/src/api.ts)

- Define a browser-safe saved-result schema alongside the existing turn contracts. Change `PublicPlanner.research` to carry the public evidence on `answerCard` before it returns. Next, change `publicResult` and the React API parser to retain it. `SourceCitation` supplies the checked date, while `GroundedAnswerCard` supplies `dataKind`, `dataOrigin`, `dataDate` and supporting fields. General web answers can carry their verified quote-to-source links. Preserve `partial`, `needs_input` and `incomplete` as distinct outcomes.
- Project only approved public fields into the job result at the server boundary. Accept public source URLs after validation and filtering of private or credential-bearing parameters, preserving legitimate public identifiers. The existing store can hold the versioned result in its JSON column. Read old `{title, url}` rows with “date unavailable” and retain their original links. [Turn schemas](../../src/core/turn.ts) · [Store](../../src/server/workflow_store.ts)
- **Acceptance.** Enqueue a synthetic benefits question through Hono, finish it, reopen the store and read it through the React API. Assert the original `dataKind`, `dataDate` and `lastCheckedAt` all the way through. A dated official answer, stored example, private program, old row and missing-field answer each retain the correct label. The UI and spoken renderer agree on dates and amounts. Extend the current durable-workspace test, which checks the resulting URL. [Durable workspace tests](../../tests/e2e/durable-workspace.test.ts)

### PR 2 · Restore the next decision after an authentication handoff (2–4 days)

On the committed baseline, a real practice-browser login turn offered `auth-done` and `auth-cancel`. After detach → recover → resume, the handoff was still `waiting`, but the response had no new turn ID and the companion offered zero choices. The main window still has fallback buttons that send generic text. Recovery also uses `PILOT_PROFILE=personal` while workspace access can recognize a completed personal-device setup. Those are separate product decisions currently expressed in different places. [Recovery API](../../src/server/app.ts) · [Session](../../src/orchestrator/session.ts) · [Companion decisions](../../web/src/companion.ts) · [Window fallback](../../web/src/conversation.ts)

- After re-observing a live, unexpired handoff, issue a fresh `turnId` with the allowed choice keys bound to its `handoffId`. Use the existing `choose` validation for the main window and the Electron overlay. The resident controls credentials, CAPTCHA and actual submission. Completion still requires the expected page evidence.
- Have health and session creation consult one server-side recovery eligibility decision. Roll it out first to the existing personal pilot, then to completed personal-device onboarding with explicit recovery opt-in. Shared devices and an undecided setup get ephemeral sessions. Re-evaluate eligibility when settings change. Keep the writer lease, five-minute detach window and microphone-off restart. Saved public jobs and live browser authority have different lifetimes. [Recovery leases](../../src/server/recovery.ts) · [Choice contract](../../src/core/choices.ts)
- **Acceptance.** Refresh during the practice login. Use keyboard, voice and the overlay to finish or cancel. An old held key, old writer or expired handoff produces zero actions. Stop interrupts immediately. Refresh during field confirmation still requires a fresh request and approval. Cover both first-run personal settings and forced shared mode. [Recovery tests](../../tests/e2e/pilot-recovery.test.ts) · [Held-approval tests](../../tests/e2e/held-approval-ui.test.ts) · [Native accessibility harness](../../apps/desktop/test/native-a11y.cjs)

### PR 3 · Let residents hear and manage their research (4–6 days)

The worker already claims jobs, fences late completions with a lease token and resumes eligible work when the app opens. Today the panel refreshes only while expanded. A question needing input copies its original prompt back into a text box. This leaves a resident who delegated work by voice with a visual search to do later. [Workflow panel](../../web/src/workflows.tsx) · [Worker](../../src/server/workflows.ts)

- Extend the existing workspace routes with a result revision, acknowledgement and a targeted answer to a pending question. Use the same job ID for “read my result”, “what is waiting?”, cancel and delete. If several jobs fit, offer a short numbered choice. An answer that changes the research scope requires fresh consent. Reuse a request ID when retrying an ambiguous enqueue. Persist acknowledgements per owner, job and result revision.
- Wire those actions into conversation as well as HTTP. Today `Workflows.bind` reduces an enqueued job ID to a boolean. Return the ID to the foreground turn, and bind a scoped read operation for a later session to find the owner's results. The UI can continue using `GET /api/session/:sid/workspace`. A proposed `POST /api/session/:sid/workspace/research/:jobId/ack` acknowledges only the revision the person actually opened or heard. Both callers use the same store operation. An interrupted reading can still be requested again. [Session binding and routes](../../src/server/workflows.ts) · [Approval consumer](../../src/orchestrator/application.ts)
- Offer a generic “조사 결과가 준비됐어요” cue at the next quiet, consented moment, including when the panel is closed. Read the subject, result and source on request. Let the panel, keyboard and voice act on the same state. “멈춰” interrupts foreground activity immediately. “맡긴 조사 취소” cancels the selected job. Defer cues during authentication or muted speech and drop them on a switch to a shared profile. Poll one lightweight revision/status feed while the session is active. Existing foreground progress can continue to use its own sequence. [Speech and session UI](../../web/src/conversation.ts) · [Foreground progress](../../src/core/progress.ts)
- **Acceptance.** Complete the opening journey using voice only and again using the keyboard. Close the app after enqueue, reopen, and find the result without expanding the panel. An acknowledged revision stays quiet on the next launch. Cancel a running job and verify that a late worker cannot publish its result. A shared user sees and hears zero personal results. Expand the SQLite tests and run the same claim/acknowledgement cases on PostgreSQL when that backend is deployed. [Store tests](../../tests/unit/server-workflows.test.ts) · [Workspace UI tests](../../tests/e2e/workspace-ui.test.ts)

## Optional institutional pilot

Start once a caseworker team identifies a recurring lookup, names an operator and can provide an evaluation workspace. This track can proceed after PR 1. An existing OpenBot installation makes it cheaper to test. Compare time to the correct official source against the team’s usual process.

1. **Reuse the lookup code.** Give the institutional service a narrow input consisting of a public program ID and requested field, such as required documents or application method. Return the value, source, source date and check date, or a clarification/unavailable result. Reuse the TypeScript welfare provider and answer-card code. The welfare agent holds mutable conversational selection, so use explicit IDs or per-thread instances. The service takes catalog credentials only. Keep resident HTTP sessions, cookies, vaults, recordings, files and guardian messaging outside this process. [Welfare agent](../../src/agents/welfare/agent.ts) · [Welfare providers](../../src/agents/welfare/data/index.ts)
2. **Build the AG-UI adapter.** Implement a separately authenticated `POST /ag-ui` with run/thread IDs, cancellation and bounded inputs. Select public fields before data enters a hosted conversation. A downstream redactor cannot remove information the workspace has already received. Accept the normal OpenBot system envelope and multi-turn history while authorizing only the selected lookup. Tool declarations and forwarded state confer no permission. Stream a visible answer with its source link and dates, plus versioned structured state for an optional card. The existing probe exercises six SDK events for exactly one fixture question. It does not test OpenBot rendering or registration. [Probe server](probe/check.py) · [Client assertions](probe/client.cjs) · [OpenBot role and endpoint contract](https://github.com/CopilotKit/OpenBot/blob/v1.1.2/docs/coworkers.md)
3. **Prove it in the workspace.** Register a `remote-ag-ui` Bot in `agents.yaml` or Bot Setup with an endpoint credential. Configure the exact allowed host for a private deployment. Run `test-connection`, then perform an actual lookup, open the source, reload the conversation and verify the same citation. Test parallel threads selecting different programs, credential revocation, cancellation, missing source data and a supplied write tool. Require zero resident access and zero tool executions. Track operator effort, retention settings and cost per sourced answer before expanding. [Configuration](https://github.com/CopilotKit/OpenBot/blob/v1.1.2/docs/configuration.md) · [Bot API](https://github.com/CopilotKit/OpenBot/blob/v1.1.2/api/openapi/bots.yaml)
4. **Expand one consumer at a time.** A second structured client can call the same lookup via MCP. A team that works in Slack or Teams can pilot one channel with staff identity, scoped grants and revocation. Before multi-user rollout, require staff sign-in, scoped lookup credentials and isolation between staff. Leave computers disabled for catalog lookup. If a future workflow requires one, provision per-person sandboxes. The Kubernetes evaluation permits a shared computer. The institution owns SSO, audit retention, backup/restore and licensing. Resident-wide Automatic Learning, general shell access and standing write grants offer little leverage on the return-to-result journey. ## How to decide whether to expand

Use **independently completed tasks / attempted tasks** as the resident measure. Compare the current and proposed flows using the existing pilot protocol with 3–5 blind or low-vision participants and synthetic data. Count help requests, time to retrieve the answer, whether the person can identify its source and next step, and whether they understand who controls the browser. Exercise installed Windows with NVDA, a physical microphone, keyboard-only use and interruption while speaking. Check the declared Korean, English, Chinese and Japanese result/choice paths. Browser automation covers the contracts. Participant observation establishes whether the change helps. [Study protocol](../user-test/plan.md) · [Native test harness](../../apps/desktop/test/native-a11y.cjs)

Roll out the inbox and routines separately on personal devices. Keep the existing manual research panel available while measuring completion. Log outcome code, duration, unexpected duplicate deliveries and provider cost per completed lookup without storing prompts, identifiers from documents, or field values in telemetry. Any stale approval executing, cross-profile disclosure, duplicate consequential action or unsupported success claim fails that release. Disable the affected feature independently and keep existing saved results readable during rollback. [Event contract](../../src/core/events.ts) · [Task evidence verification](../../src/orchestrator/task_review.ts)

**Engineering baseline, November 21.** Four selected unit suites passed 30 tests with two optional PostgreSQL cases skipped. The workspace UI, durable workspace and pilot recovery suites passed all 15 tests on both a clean export of `2bfc330` and the working tree using local fixtures and Chromium. A separate Hono/browser handoff probe on that commit observed the two choices before detach and zero after resume. The citation projection probe retained only `title` and `url`. These checks establish a baseline for PRs 1–3. Packaged accessibility, participant outcomes and a live institutional OpenBot deployment still need their respective trials.
