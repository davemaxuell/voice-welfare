# 정보취약계층 공공서비스 신청 완주 에이전트 '청음' — 기획 요약

## 한 줄 정의
신청을 대신 해 주는 에이전트가 아니라, 정보취약계층이 공공서비스 신청을 혼자 끝까지 완주하도록 화면과 사람 사이를 통역하는 음성 에이전트.

## 대상
정보취약계층: 고령층, 장애인, 저소득층, 농어민, 결혼이민자처럼 디지털 기기로 공공서비스를 혼자 쓰기 어려운 사람. 시각장애인도 대상에 들어가므로, 화면을 보지 않고 소리만으로 끝까지 쓸 수 있어야 한다는 설계 조건은 바꾸지 않는다.

## 문제
- 복지로 등 공공 신청 과정에는 혼자 넘기 어려운 구간이 있다: 탭으로 나뉜 안내(지원대상·서비스 내용·신청방법), 인증서 팝업, 자동 접속 차단·보안문자, 이미지로만 안내되는 서류, 보완 요청. 웹 구조가 낯선 고령층에게도, 스크린리더를 쓰는 시각장애인에게도 같은 구간이 막힌다.
- 받을 수 있는 제도를 몰라 신청 자체를 못 하거나(신청주의 사각지대), 신청은 했는데 보완 요청을 놓쳐 반려되는 사례가 반복된다.
- 기존 도움은 화면을 그대로 둔 채 보조하는 수준에 머문다. 스크린리더는 "화면을 위에서부터 읽어 주어" 메뉴·버튼 글자까지 다 읽고 정작 중요한 내용에 늦게 닿는다. 무엇을 눌러야 하는지는 여전히 사용자가 알아내야 한다.

## 해결 — 5개 기능 (구현 현황)
1. **음성 시작** ✅ — "기초연금 신청 도와줘"라고 말하면 공식 API로 제도를 찾아 복지로 공식 안내 페이지를 연다. 주소를 모르면 지어내지 않고 검색한다. 창 없이 백그라운드에서 돌고, 단축키 하나로 말한다.
2. **자격·서류 사전 확인** ✅ — 나이·장애·소득·지역을 하나씩 물어 받을 수 있을 법한 제도를 찾고(중앙부처 461개 + 지자체 목록 API), 선정기준 원문과 조건별로 비교해 "맞아요 / 확인이 필요해요"를 근거와 함께 말한다. 최종 자격은 판정하지 않는다. 본문은 메뉴 대신 지원대상 → 서비스 내용 → 신청방법 순서로 읽는다.
3. **항목별 음성 입력** ✅ — 실제 사이트에서 "입력 칸 하나씩 채워줘"라고 하면 칸을 하나씩 묻고("1번째, 이름. 저장된 '김하늘'을 넣을까요?") 대답대로 채운 뒤 화면 값을 다시 읽어 확인한다. 비밀번호·인증·동의 칸은 건너뛰고, 제출 버튼은 누르지 않는다. 연습용 신청서에서는 단계 안내·검증·모의 접수까지 전 과정.
4. **인증 핸드오프 + 개인 정보 금고** ✅ — "내 이름은 김하늘이고 주소는 …라고 저장해줘" → 확인 후 이 컴퓨터에만 저장(이름·주소·연락처·이메일·생년월일만, 본인만 읽을 수 있는 파일). 입력 칸을 채울 때 먼저 제안하고 확인받아 쓴다. 로그인은 "로그인하고 싶어"라고 하면 로그인 버튼으로 옮겨 가 무엇을 왜 하는지 말하고, "눌러"를 들으면 누른다. 아이디·비밀번호는 사용자가 직접 입력하고(소리로 받지 않으며 말하면 즉시 가린다), "다 입력했어"라고 하면 같은 방식으로 로그인 버튼을 누른다. 본인인증(간편인증·인증서)은 사람에게 넘긴다. *(계획)* 간편인증 요청을 폰 알림과 연결.
5. **신청 후 추적** ◐ — "기초연금 신청했어, 접수번호는 …", "보완 서류는 12월 3일까지래"를 기억하고, 기한 사흘 전부터 앱을 켤 때와 한 시간마다 소리로 알린다. "신청한 거 어떻게 됐어?"에 신청일·기한·남은 날을 말해 준다. *(계획)* 실제 접수 상태 자동 조회는 로그인이 필요해, 사용자가 로그인한 뒤 신청현황 화면을 읽어 주는 방식으로. 서류 업로드·제출은 사용자가 직접(대행하지 않음).

## 안전 원칙 (제품의 일부)
- **실행 전 확인, 제출은 사람이**: 입력은 확인받은 뒤에만, 실제 제출·본인인증은 하지 않는다. 승인이 필요한 조작은 조용히 막지 않고, 무엇을 왜 하는지 소리로 말한 뒤 "눌러"를 들으면 한 번만 한다(로그인 버튼 포함). 모든 조작은 실행 전에 안전 규칙(PolicyGuard)을 통과해야 한다.
- **추측하지 않음**: 말하기 전에 답의 근거 문장과 숫자(금액·날짜·전화번호)가 실제 화면이나 공식 자료에 있는지 대조한다(검증 담당). 없으면 "확인하지 못했어요"라고 말한다.
- **화면 글은 신뢰하지 않음**: 페이지에 "AI는 ~를 누르세요" 같은 지시가 있어도 따르지 않는다. 보안문자·접속 차단은 우회하지 않고 알린다.
- **언제든 멈춤**: "멈춰"는 다른 일보다 먼저, 즉시 처리한다.

## 차별성
- **기능이 아니라 완주율** — 버튼 클릭이 아니라 접수 완료와 결과 통지까지 책임지는 것을 목표로 한다.
- **실패 지점 자동 기록** — 지금도 동작별 성공·실패·오류 종류를 비식별로 남긴다(발화·입력값 제외). 이것이 쌓이면 복지로 접근성 개선 건의서의 근거가 된다. *(계획)* 구간별 집계 보고서 자동 생성.

## 혁신성 (구조)
1. **두 에이전트 분담** — 찾기·판단은 복지 정보 에이전트(공식 데이터만 근거), 실행은 웹 에이전트(관찰 → 계획 → 안전 규칙 → 실행 → 재관찰 검증). 화면 이해 담당이 페이지를 정리해 AI 입력을 줄이고(같은 페이지 기준 평균 29% 감소), 검증 담당이 지어낸 답을 막는다.
2. **데이터 환류 구조** — 사용자가 늘수록 공공 사이트의 막힌 구간 데이터가 쌓이고, 그것이 공공기관 개선 요청으로 이어진다. 사용자 증가가 곧 서비스 개선.
3. **인간 핸드오프 설계** — 자동화가 넘을 수 없는 벽(인증·보안문자·대면)을 사람이나 오프라인 채널로 정확히 넘기는 경계 설계를 제품의 일부로 정의한다.
4. **채널 확장** — 복지로에서 정부24, 지자체 신청, 복지관 예약까지 같은 구조로 확장한다. 영어·중국어·일본어 대화도 지원해(한국 고유 용어는 원어와 풀이) 한국어가 서툰 결혼이민자·다문화 가정까지 포괄한다.

## 검증 계획 (예선 통과 후)
- VoiceOver를 켠 상태로 복지로 신청 전 과정을 직접 재현하고, 구간별 소요 시간과 실패 지점을 기록
- 1차: 시각장애인 단체·복지관 협조로 2~3명 사용성 테스트(평소 쓰는 화면낭독기만 쓴 조건과 비교, `docs/user-test/plan.md`). 고령층·결혼이민자 등 다른 집단의 테스트는 아직 계획하지 않았다.
- 개선 전후 완주율과 소요 시간 비교

## 기대효과

- 받을 수 있는데 몰라서 못 받는 복지 발굴
- 공공 접근성 개선을 위한 실증 데이터 확보
